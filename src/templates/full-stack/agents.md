# Agent Notes

Bun full-stack app generated by create-shibumi. Hono routes, Zod validation, Alpine behavior, Drizzle + SQLite under a persistent volume. All source is owned by this project.

## Commands

```sh
bun dev          # Ship wrapper starts hot reload on the configured app port
bun dev:app      # plain watch mode on PORT (default 3000)
bun test         # route, security-header, migration, backup, restore tests
bun run check    # TypeScript check
bun run build    # bundle src/server.ts to dist/server.js
bun db:status    # applied and pending migrations
bun db:migrate   # backup (when needed), then apply pending migrations
bun db:backup    # manual VACUUM INTO backup with sha256 sidecar
bun db:restore <backup>  # offline restore; stop the app first
bun ship         # build image, upload, deploy via shibumi-server
bun ship:webhook # opt in to push-to-deploy; --off reverses it
bun run shibumi add <name>  # install an extension (auth, email); --dry-run previews
```

## Routes and templates

- `src/app.ts`: routes and the HTML page. `src/server.ts`: boot ordering and shutdown. `src/env.ts`: environment schema (`PORT`, `DB_PATH`).
- `src/db/schema.ts`: Drizzle schema. `src/db/migrations/*.sql`: tracked SQL migrations, applied in filename order by the owned runner. `drizzle-kit generate` may draft a migration from a schema change; review it, then commit both.
- Static assets under `public/`, served at `/public/*`. Alpine is the vendored CSP build; register components in `public/app.js`.

## Trust boundaries and validation

- Environment goes through `src/env.ts`; request input through Zod at each route.
- The `SECURITY_HEADERS` set in `src/app.ts` is asserted verbatim by tests on every response class. The CSP allows no inline or eval'd script.
- Add no unauthenticated mutation endpoints (POST/PUT/PATCH/DELETE); tests fail if a route registers one. The single exception is the demo `POST /api/counter`: one shared clamped row, no body read, per-IP rate limit. Real write examples live in tests, which insert through `db` directly; anything touching user data needs auth first (`bun shi add auth`).

## Database

- Path: `DB_PATH`, default `data/app.db` locally, `/data/app.db` in the container (persistent named volume `app_data`). WAL, `foreign_keys ON`, `busy_timeout 5000` applied on every open.
- Boot ordering: pre-migration backup (existing database with pending migrations), apply migrations in `BEGIN IMMEDIATE` transactions, then serve. A failed migration rolls back, the process exits, the health check never passes, and the previous deployment stays live.
- Backups: `VACUUM INTO` snapshots in `<db-dir>/backups/` with sha256 sidecars; newest 5 kept; refused when free disk is under 2x the database size.
- Restore: `bun db:restore <backup>` with the app stopped; checksum verified, temp-and-rename swap, stale WAL/SHM removed.
- Rollback semantics: `bun ship --rollback` reverses the image only. Schema and data changes stay; restore a pre-migration backup for those, then redeploy the matching code.

## Files Ship generates

`bun ship:setup` writes `shibumi-server.json` (committed) and stores SSH targets in `~/.config/shibumi/config.json` (never committed). `scripts/ship.ts` is owned vendored source; update with `bun ship:update`.

## Secrets and runtime config

Set production env vars (secrets, per-deploy config) on the server, never in git or the image:

```sh
bun ship:env set KEY=VALUE      # one or more
bun ship:env import .env.production  # bulk from a local file
bun ship:env list               # names only
bun ship:env rm KEY
```

Values are stored per-app on the server and injected at deploy; run `bun ship` to apply. Non-secret tunables that belong in git live in `src/config/*.yaml` instead.

## Checks required before commit

`bun test` and `bun run check` must pass. Schema changes require a matching committed migration. The image copies `dist/`, `dist/migrations/`, `public/`, and `package.json`; update the Dockerfile and `.dockerignore` together if runtime files move.
